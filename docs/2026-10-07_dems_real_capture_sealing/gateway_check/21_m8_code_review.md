## 3. Carried questions

**1. D140, the media-session token.**
- Constant time: one `timingSafeEqual` over two 32-byte buffers (`media-stream/token.ts:133`); the length is fixed before it (`:129-131`); the MAC is checked before any claim is read (`:136-142`); one refusal code for every mismatch (`:115`). Sound.
- In the MAC (`token.ts:87-89`, `:91-105`): the label `dems.media-session/1\0`, the payload (version, file, `expiresAt` 48 bit, 8-byte nonce, length-prefixed evidence ID), then the length-prefixed operator ID and auth-session ROW ID taken from the presenting request. The encoding is unambiguous. Not in the MAC: the device, the range. Key: named secret in the credential store, HMAC inside `use` (`store-door.ts:48-66`).
- Replay inside the TTL by another client that holds the operator's session credential: it verifies (same operator, same session row). That client could call op 88 itself, so nothing is gained; without the credential the token opens nothing (`service.ts:315` 401 first).
- Sign-out while a token is live (read, not run): stage 4 resolves the credential from the database on every request (`modules/identity/sessions.ts:236-262`, no cache); an ended session gives an anonymous principal (`plugins/authenticate/index.ts:206-218`), the guard's rule of op 88 refuses before the handler. So every NEW request dies at sign-out. An answer already in flight is not cut (R93-08). No test covers either half.
- What logs the path: the Core's request line holds the pattern `/media/:token` (`plugins/logger/request-log.ts:52-55`) and every log object passes the shared blanking rule that knows `mts_` (`logger-options.ts:216-221`); a real token is 92 characters, under the router's 100 (`EVIDENCE_ID_PATTERN` is fixed length). The Vite dev proxy prints it on a proxy error (R93-09). The web player logs the numeric media error code only (`sealed-player.tsx:268`), never `currentSrc`; the mobile player logs file and position only (`:247`), and swallows the `replaceAsync` error (`:184-187`). Expo's network inspector: not determinable from the code (question 6).
- `referrer`: a media element sends the page as referrer, never its own URL; answers carry `referrer-policy: no-referrer`. Browser history: `element.src` is no navigation. `cache-control: no-store` is set on every answer by the `onSend` hook (`plugins/response-headers/index.ts:86-87`), asserted on the media answer (`modules/media-stream/__tests__/routes.test.ts:246`). **3. Range serving.**
- Plaintext before the tag: no. `openFragment` returns `Buffer.concat([decipher.update(stored), decipher.final()])` (`credential-store/fragment-cipher.ts:183`); `final()` throws before the expression has a value, and the catch returns nothing. A fragment is read whole and opened whole before one byte is yielded (`source.ts:191-201`).
- Disk: the unit writes no file (`source.ts`, `service.ts`: no write call).
- A failed tag: first piece of the range, clean 409 before the status line (`service.ts:349-356`); later, the generator throws, Fastify destroys the response because headers are sent (`node_modules/fastify/lib/reply.js:845-853`), bytes of the failed fragment are never yielded. A `bytes=0-` request on a file whose fragment 1 fails gets the clear header bytes and then the cut, not the 409: by design.
- Abort and back-pressure: the package reader opens and closes its handle inside each `readRange` (`evidence-verify/package-reader.ts:82-93`), so no handle spans a `yield`; `Readable.from` pulls one piece at a time; on a client abort Fastify destroys the payload (`reply.js:861-869`), the generator's `finally` writes the range row. One fragment in memory per request.
- `content-length` on a cut stream: the full range length was sent; the connection is destroyed, so the client sees a short body on a closed connection (asserted in-process, `routes.test.ts:514-517`; a real client is gate 94).
- Range edges (`ranges.ts:27-50`): `a-b`, `a-`, `-n`; end clamped; start past the end and `-0` give 416; last below first, several ranges, another unit give the whole file; 15 digits at most. Fragment boundaries are row 84's `planRangeRead`, re-checked for the whole file at plan time (`source.ts:138`).
- Truncated last fragment: a file shorter than the manifest's `bytes` is refused at plan time (`source.ts:124`); after the plan is cached, a short read is `CAMERA_FILE_UNREADABLE` (`source.ts:158-171`). Sound.

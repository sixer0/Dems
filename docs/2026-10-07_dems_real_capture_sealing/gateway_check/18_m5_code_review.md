## 3. The carried questions

**1. D170 — is every protocol-4 record that 71b consumes shaped as 71a emits it; where does the fake worker differ?**
Yes for the shape; one behavioural difference in the stub, none in the hand-fed fake that changes a result.
- Emit side: `apps/capture-worker/src/audio.c:160-170` writes `kind, deviceId, role, index, fromSample, sampleRateHz, capturedAtMs, reason, correlationId, appliedDelayUs`; `index` is `++intervals` (1-based, start = 1 at sample 0, `:589`); `capturedAtMs = (t0_real + from_sample * US / SR) / 1000` (epoch ms); the record is written BEFORE the ACK (`:204-212`). `AUDIO_TIMELINE_END` is `samples, sampleRateHz, intervals` (`:658`). The role index is fixed at plan parse (`capture_worker.c:172`: PRIMARY = 0), so `role[cur_map]` cannot mislabel after op 80 reordered the selector.
- Protocol: the strict schema `packages/capture-protocol/src/index.ts:765-798` has exactly those members and refuses a start that is not index 1 at sample 0.
- Consume side: `capture-session/index.ts:521` (start row: `record.index` -> `seq`, `mediaMsOfSample(fromSample, sampleRateHz)` -> `from_media_ms`, `capturedAtMs` -> `from_at`), `:866-878` (switch), `:560` (end). Units agree: samples -> file ms with the priming origin (`:129-131`), epoch ms -> `bigint`. `seq` is 1-based in the table, the record, op 82 (`api/sessions.ts:176`) and the simulator (`api.ts:803`).
- The fake of the db test (`session-capture.db.test.ts:269`, `:329`, `:347`) hand-writes the same ten members. One ORDER difference: it sends `AUDIO_TIMELINE_END` before the stop, the real worker sends it while stopping; the supervisor still delivers records then (`supervisor.ts:687-715` has no `stopping` test) and the listener is attached until `release`, so the close of the last interval holds — read, not run.
- The process stub differs as in R74-17. What no test of the Core's path exercises: the late-acknowledgement and the not-RECORDING cases of R74-06.

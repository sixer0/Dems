## 2. Risk statements (not built, by the brief)

**R74-14 (2) - "Nothing was recorded" while a camera file exists.** In real capture `captureDurable` is derived at rehydrate from "a fragment ROW exists". A Core that dies between the worker's first durable fragment and the insert of its row restarts with the session in FAULT and `captureDurable: false`, so both clients present a failed start for a session that has media on the disk. Nothing is lost: the boot step `sealing.resume` decides by the files and seals the session as an interrupted recording; the wrong sentence is shown from the start of the Core until that seal moves the session. Likelihood: a process death inside the few milliseconds between the worker's fragment and the first row insert of a session, i.e. only in the first seconds of a recording. An operator sees a recovery screen saying nothing was recorded, then an evidence item appears for that session. A fix needs a FILE seam into the engine host: the engine folder may not touch the file system (static rule `OUTSIDE_WORLD`), and the existing door `markCaptureDurable` acts on a RECORDING session only - so it is a new host dependency provided by the capture unit plus a door or an input of `captureDurableAtRehydrateTransition`: a design step, not a few lines.

**R80-05 - `backendUnreachable` signed for a backlog.** On the `omlx-server` backend every chunk the seal's close-out gives up gets the code `TIMEOUT` (`sealing/finalize-transcript/bounds.ts`), and `TIMEOUT` on that backend is read as "backend could not be reached" (`handler.ts` `isUnreachableCode`): manifest field 122 is signed `true` and verify says `PARTIAL_BACKEND_UNREACHABLE`. False when the server answered every request but had not finished its backlog at the bound. Needs a session whose backlog outlasts the seal's wait (a long recording, a slow or busy model server); frequency not measured. The operator reads "The transcription backend could not be reached for part of the recording." on an item whose backend was up - permanently, it is in the signed manifest. The lost text is still reported correctly (PARTIAL, the failed-chunk count); only the stated cause is wrong. A fix needs a new chunk code (`TranscriberErrorCode` lives in `apps/transcriber/src/types.ts`, not in shared) kept out of `isUnreachableCode`, AND a ruling on field 122: "a request got no answer" only, or a signed statement of its own for the backlog (a manifest change).

## 4. Decisions for the controller

1. **R80-08: the row cannot rebuild a revision record.** `transcript_revisions` stores the body's HASH, not `body.changes`; D186's "re-appended from the row's stored body" is not possible without a column (a migration). Built instead, inside the ruled order: the STAGED file carries the body and the table judges it (promoted only when every record matches its row by number, hash, signature and a body hashing to the row's hash). Residual: a committed row whose staged file is lost or damaged before the next start cannot be healed - one error-log entry, op 86 keeps answering 503 for that item. Only a `body` column closes it.
2. **While a staged file exists, verify fails V-14 `UNEXPECTED_FILE`** on that package (between stage and rename; after a crash until the next append or start). Tolerating the name is a change in shared `evidence-verify` (F-M7c's area): not made.
3. R80-08 also: one in-process lock per package around a whole append; op 86 reads the staged list (read-only) while a rename is pending; the db fault injection is a deferred constraint trigger created as owner on the throw-away clone.
4. **Item 6: the simulator's sending device is `'TABLET'`** - the only device ID a device-console simulator knows (its pairing rows use it). A phone app's simulator writes the same ID.
5. **Item 2: a stored read that FAILS answers `503 NOT_READY`, not 404** (a job that may exist is not denied); a queued job whose request cannot be read ends FAILED `EXPORT_REQUEST_NOT_FOUND` with an error-log entry `EXPORT_REQUEST_NOT_READ`.
6. **R74-08: STARTED is still told** when `begin` was cut short by a stop (as before: STARTED, then STOPPED); its camera list then holds only the cameras opened so far.
7. Item 1: the scope on op 85 is walked through a temporary role change of the TECHNICIAN (the walk's own operation 12), restored in the same block.

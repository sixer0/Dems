## 2. The data step: its rule, and what it changed on the seeded throw-away database

**Rule (conservative, as instructed).** A row whose list does not satisfy the CHECK gets the EMPTY list `[]`. Nothing is translated: a token is no code, no stream row says what it meant, and no default profile may stand in for a production camera (decision C36). `[]` is what adoption stores today when no stream half ran; the camera keeps its row, address, credential and adapter, and needs ONE connection test before it can be assigned. The WHOLE list goes, also when only one element is foreign (DRIVER DECISION 3): a list with a foreign element was not written by the code that mints codes, so none of its elements is known to be one.

## 3. THE STATED LIMIT (for the controller and review 60)

The CHECK holds the FORM, not the origin. A camera whose ONVIF tokens happen to be of the code form (`PROFILE_1`, `MAINSTREAM`) passes it, and a list of such tokens stored before row 51 is NOT emptied by the data step (measured: M11S-4, "THE STATED LIMIT"). What makes an element a MINTED code is its row in `capture_device_streams`; that is held by adoption (`assertAdoptedProfiles`, `CS/src/modules/capture-discovery/adoption.ts:107`), not by the database. The effect of such a left-over list is bounded: no stream row exists for it, so the production adapter refuses its open (`CAPTURE_PROFILE_UNKNOWN`, row 51's record) - a camera that cannot be recorded from, not a wrong recording.

A wider data step was considered and NOT built (DRIVER DECISION 4), because it changes rows that satisfy the CHECK and the instruction named the narrow rule: "for a camera of adapter `ONVIF_RTSP`, empty the list when an element has no stream row". Its statement, NOT RUN:

```sql
UPDATE public.capture_devices AS d SET profiles = '[]'::jsonb
 WHERE d.adapter_kind = 'ONVIF_RTSP' AND d.profiles <> '[]'::jsonb

                WHERE NOT EXISTS (SELECT 1 FROM public.capture_device_streams AS s WHERE s.device_id = d.id AND s.profile = e.code));
```

Know before ruling: it would also empty the list of a camera whose stream rows a demo reset removed (`capture_device_streams` is not a kept table, section 7) - which is the state that camera is in anyway.

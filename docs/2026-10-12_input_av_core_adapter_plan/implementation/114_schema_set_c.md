## 3. AS BUILT, for rows 116 and 117 (what the database accepts and refuses)

1. **Write**: `INSERT INTO public.installation_acceptances (accepted_at, accepted_by, software_version, core_device_id, site_name, room, site_address, steps, diagnostics) VALUES (...)` as the runtime role; `id` is the database's. A second INSERT while one row has `revoked_at IS NULL` answers **23505**, constraint `installation_acceptances_in_force_key` - also when two requests arrive at the same moment (measured: of two open transactions exactly one commits). Map it to the operation's "an acceptance is already in force".
2. **Revoke**: ONE statement sets all three columns - `UPDATE ... SET revoked_at = $1, revoked_by = $2, revoke_reason = $3 WHERE id = $4 AND revoked_at IS NULL`. The reason is 5 to 500 characters. No other column can be updated (42501), and no row removed.
3. **`steps`**: a JSON list of 0 to 32 FLAT objects (members are texts, numbers, booleans or null). **NOT A MEMBER NAME: `code`** - it is one of the 28 denied names, as are `token`, `secret`, `username`, `password` ...; a step's detail code needs another name (the fixture uses `id`, `passed`, `detail`). A near name (`my_code`, `tokens`, `Password`) is accepted: the rule is the exact name, as for an audit detail.
4. **`diagnostics`**: a JSON object, at most four levels deep - the Core's `DiagnosticsRun` as it is (`id`, `startedAt`, `completedAt`, `checks[]` of `{ id, label, status, detail, params{...}, resolvesAt }`) fits; a map inside `params` does not.
5. **Bounds**: every text in either document at most 200 characters and free of control characters (NO line break, no escape sequence: normalise device and diagnostic text before the write); `steps` at most 8,192 bytes, `diagnostics` at most 16,384 bytes, both counted on the database's text form (a blank after every colon and comma: about 2% more than `JSON.stringify`).
6. **Site**: `core_device_id`, `site_name`, `room` are single-line texts of 1 to 200 characters (copies of `core_device.id`, `.name`, `.room` at acceptance); `site_address` NULL or 1 to 500 characters, line breaks allowed; `software_version` single line, 1 to 64.

## 10. Driver decisions (for the controller to confirm)

1. **The shape rules beyond the design's two words** ("CHECK array, at most 32 elements", "CHECK object"): each step a flat object; the diagnostics at most four levels deep; the denied names at ANY depth. They follow S13-13 and the shape of the Core's own diagnostics run; a contract of row 116 that needs a deeper document needs a later set.
2. **The bounds**: 8,192 and 16,384 bytes; 200 characters without a control character per text (not 500: PostgreSQL's repetition bound is 255). The design gave no number for either.
3. **`code` is refused as a member name** in both documents, because the denied list is taken as it is (the list an audit detail is held to). Row 116 names a step's detail code otherwise.
4. Single-line bounds on `software_version`, `core_device_id`, `site_name`, `room` (the design: "1 to 64 characters" for the version, none for the three copies; `core_device` itself has no bound, so an installation whose room name is longer than 200 characters or holds a line break could not be accepted).
5. The table is declared in a schema file of its own, `installation.ts` (group `installation`), not in `capture.ts` or `core.ts`; `noSecretKeysAnywhere` was added to `checks.ts`.
6. The two table lists outside the schema folder (`store.ts` `ALL_TABLES`, `fixtures/minimums.ts`) and their test keys were extended by one entry each, as set B did: every count test reads them. No step on the demo database (section 2); T-48 is not in the kept set of a reset (request).

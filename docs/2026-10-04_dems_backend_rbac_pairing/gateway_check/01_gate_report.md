## Standing rules for backend module rows (decision D83, 2026-10-04)

Written by the controller after the gates of the core services (D67), the engine host (D77), the identity core (D78) and the RBAC guard (D83). They bind every row that fills a module folder under `apps/core-server/src/modules/` (plan rows W32 to W43). Sources: `implementation/21_core_services.md` §3, §4.1; `implementation/26_engine_host.md` §3, §9, §10; `implementation/24_identity_core.md` §9; `implementation/28_rbac_guard_pipeline.md` §8; `implementation/23_request_guards.md` §6.2. Where a rule below and one of those documents differ, the document of the owning row wins and the difference is reported.

| # | Rule |
|---|---|
| M1 | **Write paths.** Only the module's own folder (source and `__tests__/`), its documents and assets. The module's `index.ts` stub of the scaffold is replaced; `app.ts`, the contract, the schema, migrations, mapping, seed, core, engine, plugins and other modules are not edited. A needed change elsewhere is a finding with the exact line (`CONTRACT-GAP-n`, `SCHEMA-GAP-n`, or a request to the owner) |
| M2 | **Routes come from the registry.** `app.route({ ...routeOfOperation(operation), schema, handler })` (`routeOfOperation` from `plugins/permission-guard`), request and response schemas from the contract (`packages/shared/src/api/**`, read-only). A route that is not a registry operation, or a rule put into a route's configuration, stops the boot |
| M3 | **Who may call is stage 6, only.** No permission, role, session or device check in a handler or a route hook; no `ACCESS_DENIED` or `EXPORT_DENIED` row written by a module (the guard writes exactly one per refused call). Each module row has a static test asserting this for its folder. For 23 hosted actions the simulator checks nothing: the access rule is the only check |
| M4 | **Hosted actions** (the simulator's): `const { value, epoch, revision } = await app.engine.command(request.principal, action, ...args)`; answer AFTER it resolves, with `x-dems-epoch` and `x-dems-revision` from the outcome. A refusal the simulator reports in its result is returned from the unit and answered afterwards (it may have written a row); a thrown `Sim*Error` arrives as an `ApiFailure` with `details.simCode` — let it propagate. Use `app.engine.run(label, scope => …)` when a hosted action and rows of the module belong to one unit. Never call a simulator action directly, never read the `Sim`'s working state, never change what `engine.state()` returns, never call `engine.command` inside `app.pipeline.run` |
| M5 | **Server-native state changes** (rows of the module's own tables): one unit — `await app.pipeline.run('<module>.<operation>', async (unit) => { … })` — check-and-change in ONE statement whose row count decides (compare-and-set), `unit.audit.append({ type, actorId, deviceId, message, details })` with only the allowed detail keys, `unit.events.append(…)` where the spec asks, publications in `unit.afterCommit(() => app.publish(…))`. Reads that change nothing use `app.db.pool`. The two POST headers of API-7 are set from `app.engine.epoch` / `app.engine.revision`. Never insert into `audit_log` or `events` directly; never log `error.message` of something `unit.db` threw (use `sqlStateOf`) |
| M6 | **Audited refusals of the module itself** (not access refusals) take their place in the denial budget first: `await app.denialBudget.consume(request)`, then the unit with the row, then the answer. Beyond the budget the answer is 429 and no row |
| M7 | **Input.** The schema stage answers 422 `INVALID_INPUT`; where the specification names a specific code (`INVALID_REASON` for a too-short reason) the module maps it. A caller without the right never reaches body validation. A malformed path ID answers what the contract documents for that operation. The server does not cut text: over-long text is refused |
| M8 | **Time, identity, secrets.** Only `app.clock`; the actor of every row is `request.principal`, never a request field; no token, hash, code, password or credential in a log line, an error, an audit row, an event, a test name or a snapshot. No `Set-Cookie` on an answer to a device's bearer or public request. Nothing keys on `Host`, `User-Agent` or the presence of an `Origin` |
| M9 | **Tests.** Database tests on the helper's clones only (`useTestDatabase({ template: 'tpl_seed' })`, or `'bulk'` for volume and paging; `DEMS_TEST_STEP=<blueprint step>`), never `dems_demo` or a lane. A booted app has a RUNNING ENGINE: call `engineControl(app).useTimer(manualTimer().timer)` before the boot and count rows relative to the state AFTER boot (the first start on a fresh seed writes one `TABLET_LINK_CHANGED` row). A signed-in operator comes from the identity row's test support; a test app refuses its own cookie together with an `Authorization` header (send one credential). On `tpl_bulk`, sign in as a SEEDED operator and run the clock at `BULK_TEMPLATE_NOW` or later; page and assert by `seq`, never by `at`. A test that reads `pg_stat_activity` or `pg_locks` keys its question by its own database or a run-unique application name. In a database-free test give the principal its permissions through `app.stages.replace('authenticate', …)`; scratch routes need `passScratchRoutes(app)` after `ready()` |
| M10 | **Do not pin what other rows change.** No assertion on the total list of registered routes, the list of modules that are still stubs, the list of boot steps, or a closed set of log keys of the whole server — pin only the module's own. If an existing test of another row pins something the module changes by design, do NOT edit it: message the controller with file:line, the failure text and the smallest change (the pattern of decisions D72 and D82). The row that fills a seam deletes its own stub assertion in `plugins/readiness/__tests__/readiness.test.ts` (re-read the file first; only its own lines) |
| M11 | **Module gate (MODG).** The route list of the module equals its registry operations (both printed by a test); for every operation each documented status that the module can produce has a test and every answer validates against the contract (`validateCoreApiResponse`); the role-by-operation decision is the guard's (one allowed and one refused call per operation is enough here — the full matrix is the test row W47); `npm run typecheck -w @dems/core-server` and `npm run lint -w @dems/core-server` exit 0 without a warning; a mutation check of the module's own logic |
| M12 | **Parallel run.** Several module rows edit `apps/core-server/src/modules/*` at the same time and share the `unit` and `db` projects. A red in another module's folder is noise (P11): report it with the time, re-run, record both. At the end both whole projects exit 0 or every failure is named as another row's in-flight work. Database commands need the per-command sandbox bypass; never `cd`, not even for a read-only command; no `timeout` command (it does not exist on this host); no `rm` outside `$TMPDIR`; pre-images for untracked paths are file copies under `.cache/rollback/` |
| M13 | **What each row reports.** The handler recipe it used per operation (hosted or server-native), the status table per operation with the test for each, measured round trips for one command, every `CONTRACT-GAP-n` with the exact text the contract close-out row needs, findings, deviations, decisions for the controller, rollback |
| M14 | **Logging an error (decision D87, review finding CPB1-2).** An error is logged only as `{ err }`, never under another key (`error`, `cause`, `e`, `reason`), never spread into the log object, never as a string built from `error.message`: the query builder's error carries the statement, its parameters and the server's DETAIL as enumerable members. A server-wide static test refuses such a call. Addition to M10 (finding CPB1-1): a stand-in route for a registry operation is never registered on the real app — only on an app built without that module, or where no route exists. Addition to M5 (finding CPB1-8): reads that change nothing may use the helper `app.db.read(…)`, which answers 503 on a failed pool read |
| M15 | **Mutation checks and load (decision D88).** A mutation check never changes a file in the workspace tree, not even for seconds: it runs on a scratch copy outside the source tree or through a transform in a separate runner configuration. Whole-project suites run after a coherent change and at the end, with `--maxWorkers=2`, never in a loop; a time-out in a file the row did not touch while the load is high is re-run alone before it is judged |
| M16 | **What a unit may send (decision D96, review findings CPB1-3, CPB1-4).** A statement sent through `unit.query` / `unit.db` is ONE row statement — `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `WITH`, `VALUES`, `SET LOCAL` or `SET CONSTRAINTS` — sent in the extended protocol; anything else (`DO`, `LOCK TABLE`, `SHOW`, `CALL`, `EXPLAIN`, `SELECT … INTO TEMP`, `set_config(…)`, several statements in one text, transaction control) is refused with `UNIT_STATEMENT_NOT_ALLOWED` before it is sent. Every runtime connection and every unit pins `search_path = public, pg_temp`; production sources contain no `TEMP`, `TEMPORARY`, `search_path` or `set_config(` outside the two places that pin the path (static test). A connection lost during a unit answers 503 `NOT_READY` and turns readiness off until a probe succeeds. In a database-free test the stand-in pool must answer boot step B-1's search-path question (`standInDatabase()` / `answersBootStepOne` of the core's test support) |

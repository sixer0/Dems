## 6. Key challenges (design, with evidence)

1. **"Unchanged bound purposes" was asserted by reasoning, not by a test on the real reader.** Rows 105 and 141 changed `networkFactsOf` from null to a context, and each caller was audited by reading its null check. F1 shows that the doubles (`facts: () => null`) kept the old answer alive in the tests. Any caller whose test stubs the reader instead of calling `networkFactsOf` can hide the same regression. Recommendation: for every `.facts()` consumer, one test that goes through `networkFactsOf`.
2. **The D31 acceptance against HOST-23.** D31 ("semua kamera dari wifi dan lan sudah ada di list") expects Wi-Fi cameras in the discovery list. HOST-23 (U-RF3) admits WS-Discovery answers on the camera port only. `selectInterfaces` probes Wi-Fi, but under an active ufw the multicast answers from Wi-Fi are dropped, and a Wi-Fi camera appears only by typed address (hypothesis: the reply to a unicast typed probe passes ufw by connection tracking; not verified on .73). This is not a code defect. The controller should make sure the user's 2026-10-23 check is run the way U-RF3 allows.
3. **Physical-card exclusivity rests on identity matching outside a DB constraint** (Q96-07: service-only, no index). The service serialises through the unit pipeline (`core/pipeline.ts`, X-1), and T-11 proves one 201. Accepted, but every future writer of `capture_audio_inputs` must call `boundInputs` + `holdsCard`. No static rule enforces that today.
4. **`release: true` on two serial-less twins moves the holder to a unit the runtime will then refuse** (`MODEL_SHARED`, not opened). This is consistent with Q96-03 and the console offers nothing for an ambiguous card (`inputOffered`). A Live API caller can still do it, though, and gets `200 REENABLED` for a microphone that will not open while both units are plugged in. Consider refusing `release` when the match is `NOT_TELLABLE`.
